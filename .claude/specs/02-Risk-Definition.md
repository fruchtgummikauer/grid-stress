## Goal

This is not an EDA notebook. `team-EDA.ipynb` already did that analysis and left one explicit open
question in its closing "Findings" section: residual load's two extremes are different mechanisms
— "we need to decide whether the risk flag should treat them as one target or two." This spec
answers that question and turns the answer into a concrete, reproducible labelling methodology, per
the project's stated purpose in [CLAUDE.md](../../CLAUDE.md): flag days at risk of TSO intervention
measures, using `residual_load` as the target.

Concretely, this spec:

1. Defines **risk** in this project's terms: a `residual_load` magnitude extreme enough that TSOs
   plausibly need intervention measures (redispatch, reserve activation, cross-border exchange,
   curtailment) to keep the grid balanced.
2. Restates why the two tails are different phenomena, citing the mirror-image calendar signature
   `team-EDA.ipynb` §3.7 already found, rather than re-discovering it.
3. Defines **high residual load** risk: import needs / tight reserve margins, the "classic winter
   stress case."
4. Defines **low / negative residual load** risk: renewable oversupply, negative prices, downward
   redispatch, curtailment.
5. Derives a **threshold for each direction from `data/smard.csv` itself** — no hardcoded MWh
   figure — and does so two ways, because the record is not stationary (§6.3's finding that the
   negative share is "small, but growing and highly clustered"): a **static**, whole-record
   threshold, and a **rolling**, trailing-window threshold that only uses each day's own history.
   Both are computed and exported side by side, as candidates; this spec does not pick one.
6. Implements **Definition 1 (core, day-level)**: a per-day flag ("this might be a high-risk day")
   with a reason — the triggering hour and its value.
7. Implements **Definition 2 (intra-day)**: per-hour flags using the same threshold as
   Definition 1, and a derived time range per flagged day-direction.
8. Exports both as CSV artifacts the modeling spec can load directly, rather than leaving the
   definition as prose only.

Success means the modeling spec can import `data/risk_labels_daily.csv` /
`data/risk_labels_hourly.csv`, or the functions that produce them, and start feature engineering
against a documented, reproducible flag — without having to invent a threshold itself.

## Behaviour

### Setup

1. Repeat [03.1-setup.md](03.1-setup.md)'s loading and preparation verbatim: the data-directory
   resolver, `time_series`, `SERIES`, `DERIVED`, `YEARS`, `period_mean`/`period_energy`,
   `style_timeseries`, `DAY_NAMES`, the season mapping. One markdown cell restates that these are
   inherited, pointing at 03.1, with no re-derivation.
2. Restate, in one markdown cell, the two calendar-signature findings this spec builds on
   (`team-EDA.ipynb` §3.7 and §6.3), each in one or two lines, with no new evidence gathered for
   them here.

### Defining risk

3. One markdown section stating the project's risk definition: a `residual_load` magnitude extreme
   enough to plausibly require TSO intervention (redispatch, reserve activation, cross-border
   exchange, curtailment), and the two mechanisms it splits into — high (import needs / tight
   margins) and low/negative (renewable oversupply / negative prices / downward redispatch) — with
   one line each citing `team-EDA.ipynb`'s finding that these are structurally different (recent
   vs. stable, summer-midday-weekend vs. winter-weekday-evening).
4. State plainly that "risk" here is a **level-based magnitude** definition, not a
   probability-of-intervention model — this spec produces the candidate label a future model would
   be trained to predict, not the model itself.

### Threshold construction

5. Define the **static** basis: `high_threshold_static = residual_load.quantile(1 - p_high)` and
   `low_threshold_static = residual_load.quantile(p_low)`, each computed once over the full,
   currently-loaded record. Because it is computed from `time_series` at run time and the record's
   extent is not fixed ([03.1](03.1-setup.md)), this counts as "dynamic data input" — no literal
   MWh figure is written into the notebook.
6. Define the **rolling** basis: for each calendar day `D`, `high_threshold_rolling[D]` and
   `low_threshold_rolling[D]` are the same quantiles computed over the trailing 365 days of hourly
   `residual_load` values **ending the day before `D`** (the window is `[D-365, D-1]`) — `D`'s own
   data never contributes to its own threshold. Require at least 90 days of trailing history; days
   with less are left with an undefined (`NaN`) rolling threshold rather than one computed from
   insufficient data.
7. State the trade-off explicitly, rather than picking a side: static uses the whole record
   (including hours after the day being judged), which is fine for retrospective, descriptive work
   but leaks future information into a label for an earlier day and cannot be reproduced in a live
   pipeline; rolling is causal (only past data) but undefined for the record's first ~365 days and
   moves as more history accumulates, so the same absolute MWh level can be "risky" in one period
   and not in another.
8. Report a small sensitivity table for each direction — candidate percentile levels `{0.5 %, 1 %,
   2 %, 5 %}` — showing, for the static basis, both the resulting MWh threshold and the **share of
   days** flagged (not the share of hours: a day is flagged if any one of its hours crosses, so the
   day-share is expected to exceed the hour-share, and that gap is itself worth reporting). Select
   **1 %** as the default carried into Definitions 1 and 2 below, for continuity with the 1 %
   tail-by-rank framing `team-EDA.ipynb` §3.7 already used — stated as a recommendation, not a
   re-derivation of that number.
9. Plot the rolling threshold as a time series for each direction, against the static threshold as
   a horizontal reference line, so the divergence is visible directly. Expect — and report whichever
   way it actually comes out — the low/negative threshold to drift more than the high threshold,
   given §6.3's finding that the low tail is growing and the high tail is stable.

### Definition 1 — day-level flag

10. Aggregate `residual_load` to one row per calendar day (local `Europe/Berlin` wall-clock date,
    the same day boundary `DERIVED["date"]` already uses — not a rolling 24 h window): the day's
    maximum value and its hour, and the day's minimum value and its hour.
11. For each of the four threshold series (`high_static`, `high_rolling`, `low_static`,
    `low_rolling`), flag the day: `high_risk = day_max >= high_threshold`, `low_risk = day_min <=
    low_threshold`. A day may be flagged in both directions; this is allowed and reported as its
    own count, not silently prevented. A day with an undefined rolling threshold is flagged `NaN`
    (undefined), not `False`.
12. Build the "why": for each flagged day-direction, the triggering hour's timestamp and value,
    formatted as one line per example (`"high risk: peak 62,400 MWh at 2024-01-11 18:00, over the
    static P99 threshold of 58,900 MWh"`), demonstrated on a handful of flagged days per direction —
    this is the "day + why" Definition 1 asks for.
13. Report the count and share of flagged days for each direction × basis, and how the static and
    rolling counts diverge, especially for the low/negative direction.

### Definition 2 — intra-day flag

14. For every hour, flag it against the **same** threshold used for its day in Definition 1 (same
    percentile, same basis): `high_risk_hour = residual_load >= high_threshold` (the day's
    applicable value for the rolling basis), `low_risk_hour = residual_load <= low_threshold`.
15. For each flagged day-direction, derive the **time range** as the span from the earliest to the
    latest flagged hour that day (inclusive), even if the flagged hours within that span are not
    contiguous — state this choice explicitly, since "time range" could otherwise be read as
    requiring contiguity.
16. Demonstrate Definition 2 on the same handful of example days used in Behaviour 12, printed as
    e.g. "during 17:00–20:00 there may be high risk for the positive extreme" — the phrasing the
    spec goal asks for.
17. Plot the hour-of-day distribution of flagged hours per direction (both bases), and compare it
    against `team-EDA.ipynb` §3.7's already-established hour-of-day signature of the extremes,
    stating whether they agree.

### Export

18. Export `data/risk_labels_daily.csv`: one row per calendar day, columns for the day's max/min

## Edge cases

- **Day boundary.** A "day" is the local `Europe/Berlin` calendar date already carried in
  `DERIVED["date"]`, not a rolling 24 h window. Spring-DST days have 23 hours; this affects nothing
  here (max/min are unaffected by a missing hour), unlike the ramp series, which this spec does not
  touch.
- **Rolling threshold, insufficient history.** The record's first ~90 days have no valid rolling
  threshold at all, and the first ~365 days are judged against a still-filling window. Both flag as
  `NaN`, reported as an explicit exclusion count, never silently coerced to `False`.
- **A day flagged in both directions.** Physically plausible (e.g. a summer day with a midday
  oversupply trough and an evening demand peak) and must not be prevented or merged away — report
  its count.
- **Static basis leaks future information into past labels.** By construction (Behaviour 7): a day
  in 2022 is judged against quantiles that include 2025–2026 data. Fine for this spec's descriptive
  comparison; explicitly flagged as unsuitable for a live/production pipeline in the closing
  findings, which is exactly why the rolling basis exists alongside it.
- **Growing negative share pulls the static low threshold down over time.** §6.3 already measured
  the negative share growing; as more recent, more-negative data accumulates, `quantile(p_low)` on
  the full record trends more negative with each re-run. State this as a property of the static
  basis, not a bug — and exactly the asymmetry the static-vs-rolling comparison (Behaviour 9) is
  built to surface.
- **Time range is a span, not a set.** Behaviour 15's derived range covers gaps between flagged
  hours within the same day. If the team later wants the literal (possibly non-contiguous) set of
  flagged hours, that is available directly from `data/risk_labels_hourly.csv` — the daily file's
  range column is a summary, not the source of truth.
- **CSV format is a deliberate departure.** `smard.csv` and `rebap.csv` use German/semicolon and
  OAuth-flavoured formats respectively because they come from external APIs in that shape; these
  two exports are internal artifacts with no such constraint, and use plain comma/period CSV.
- **Missing data file.** A fresh clone has no `data/smard.csv`; the first cell fails with a clear
  message, per [03.1-setup.md](03.1-setup.md) Behaviour 1.
- **Installed-capacity data does not exist yet.** Thresholds here are in absolute MWh. If and when
  installed-capacity figures are imported, a future spec may need to re-express them relative to
  capacity — noted once (Scope/OUT), not explored here.
