## Goal

Spec 06.1 rebuilt spec 05's features for the regression notebook's forecast origin, the
availability cutoff on `DAY−1`, and proved them with a truncation test. This spec puts those features
into the boosters of **a copy of the regression notebook**. That is the "later step" spec 06.1 left
out.

The work goes into a new notebook, not into `regression-models-claude.ipynb`, for two reasons:

- `regression-models-claude.ipynb` is an approved spec output with team edits. CLAUDE.md forbids
  overwriting it.
- It stays the baseline. The new notebook carries the same windows, registry, grids and
  scoreboard, so any change in its scoreboard comes from the features. The committed source has no
  saved outputs, so its baseline scoreboard comes from a scratch run outside the repository
  (Behaviour 10).

In the new notebook, the features are **rebuilt inside `design_rows`**, not loaded from
`data/features/residual_load_features_cutoff.csv`. There are two reasons:

- The copied leakage test (§5.4) rebuilds `design_rows` from data cut at each day's cutoff. Columns
  joined from a file are never rebuilt, so they would either break that test or pass it without
  being tested.
- `actuals_lag` is still a team trial (2 h now; spec 06's default is 3 h). Built in place, the
  features follow `DATA_INFO` automatically. A loaded file would have to be regenerated after
  every change.

The CSV stays the proven reference from spec 06.1. This spec does not read it.

Spec 06.1's set has one SMARD forecast, `forecast_wind_solar` (`fc_gen_wind_solar`). It has no
grid-load forecast, because spec 05 excluded `fc_grid_load`. The regression notebook's boosters
take both. So this spec splits the `smard_forecast` group in two, and the grid-load forecast
becomes a switch of its own.

The team decided four things:

1. The new groups are **on** in the default configuration, and the new notebook's closing section
   is written from its own run.
2. `calendar` and the new `cyclical` group are **independent `True` / `False` switches**. The default
   is `cyclical` on and `calendar` off. To compare, flip both and re-run.
3. `smard_forecast` is replaced by two **independent `True` / `False` switches**,
   `smard_forecast_grid_load` and `smard_forecast_gen_wind_solar`. Both default to `True`, so the
   default booster inputs from SMARD stay as they are. Switching `smard_forecast_grid_load` off
   gives spec 06.1's forecast input.
4. The change goes into a **new notebook**. `regression-models-claude.ipynb` stays unchanged.

Success means:
- the new notebook's default run uses the new features
- it passes every carried-over self-check and the leakage test
- its scoreboard and closing section report the result
- flipping the switches still runs cleanly
- `regression-models-claude.ipynb` and spec 06's exports are untouched

## Edge cases

- **Both calendar switches off.** `calendar = False` and `cyclical = False` is allowed. The boosters
  then lose hour and day type, and the notebook runs as long as some group is on.
- **Both calendar switches on.** The columns are redundant but correct. `is_weekend` and `holiday`
  appear once (Behaviour 7).
- **Both SMARD switches on (default).** `fc_gen_wind_solar` appears once. The booster inputs from
  SMARD equal the source notebook's `smard_forecast` group.
- **`smard_forecast_grid_load = False`.** The direct boosters no longer see `fc_grid_load` and can no
  longer rebuild SMARD's residual-load forecast. The hybrids' stage 1, SARIMAX and the
  forecastability rule still use it, so the test days and the "post-processor" framing of the
  hybrids do not change.
- **Both SMARD switches off.** Allowed. The direct boosters then have no forecast for the target
  hour and are expected to lose a lot of accuracy. The notebook runs as long as some group is on.
- **`actuals_lag` changes.** The features follow `DATA_INFO` automatically. The §2.2 check and the
  §5.4 test re-verify them, and nothing else needs changing. A change in one notebook's
  `DATA_INFO` does not reach the other; the baseline comparison then compares two forecast
  settings, and the review summary says so.
- **The source notebook changes later.** The copy does not follow it. Picking up later edits of
  `regression-models-claude.ipynb` is a new spec run, not a sync.
- **Runtime.** The 11 extra columns barely change booster fit time. The three full runs in
  Behaviour 10 take about an hour each (spec 06 Behaviour 32), about three hours in total. The windows and grids are not shrunk
  to save time. The SMARD switch checks in Behaviour 8 fit nothing.
- **Warm-up and DST gaps.** The default 24-month training windows never reach the record's warm-up.
  The DST `NaN` days fall inside training windows, where the boosters handle them.

### Behaviour 15 — No `fc_grid_load` input

Overrides Behaviour 2's defaults, Behaviour 4's default row and the "hybrid stage 1" item of
Scope OUT.

| Route of `fc_grid_load` into a model | Change |
|---|---|
| booster column (`smard_forecast_grid_load`) | default `False`, **pinned**: §1.5 stops if it is on |
| `err_grid_load_recent` (= mean `fc_grid_load − grid_load` up to the cutoff) | `recent_smard_error` is split into `recent_smard_error_grid_load` (`err_grid_load_recent`, pinned `False`) and `recent_smard_error_renewables` (`err_renewables_recent`, `True`) |

| SARIMAX `exog` | already `fc_gen_wind_solar`, `holiday`; SARIMAX is off anyway |

- `FORECAST_INPUTS` (the forecastability rule, §2.4) **keeps** both SMARD
  forecasts. It only checks that they are published, uses no value, and keeps the test days

- Why: with both SMARD components a model can rebuild `fc_residual_load`

  side itself; the comparison with SMARD is then a forecast, not a post-processing of SMARD's
  residual load.
- A stage 1 without `fc_grid_load` is a hybrid linear-stage variant. Those were rejected as a tuning
  idea (spec 07, CLAUDE.md); this one is a team restriction, not a proposal to improve the score.
