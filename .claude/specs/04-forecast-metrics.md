## Goal

The project will build its own 24-hour-ahead forecast of `residual_load` and use it to flag days at
risk of TSO intervention. SMARD already publishes a day-ahead forecast of residual load
(`fc_residual_load`) and of its two components (`fc_grid_load`, `fc_gen_wind_solar`). That public
forecast is the **baseline our model has to beat**. This spec measures how good it is.

Concretely, this spec:

1. Computes the **hourly error series** `error = forecast − actual` for three pairs —
   residual load, grid load, wind + solar — for every hour both values exist, and exports it, so any
   evaluation window can be scored later without re-running this notebook.
2. Reports **MAE, RMSE, signed mean bias and `hour_count`** (the number of hours compared) for each pair, plus a normalised
   MAE so the pairs can be compared with each other.
3. Slices the error **by time** (month over the record, hour of day, season, year) and states
   whether the forecast is getting better or worse and where its weak hours are.
4. Reports the **error by residual-load level** — bins across the whole `residual_load` range. This
   is the slice that matters most: if SMARD's forecast is accurate on ordinary
   hours but degrades in the tails, the extreme cases this project cares about are exactly the ones
   the public benchmark handles worst.
5. Measures the error of the **day maximum and day minimum** of residual load — the quantities the
   risk label is built on — which the hourly error does not capture.
6. Builds a **cascaded error table** (full record → trailing 365 days → year → month → day) and a reusable
   window helper, so an "error number" can be shown for the whole record and for any window.
7. Closes with a plain **benchmark statement**: the numbers our own model has to beat, in the same
   units, with the provisional headline window and the rule for re-scoring on the modelling spec's
   own test window.

Success means the modelling spec can load `data/metrics/smard_forecast_errors_hourly.csv`, pick its test window,
and compute SMARD's error on exactly the same hours as its own model — without re-running this
notebook and without inventing a target.

### Why an error number is always "over a window"

A metric like MAE is not a property of the forecast alone; it is an average **over a set of hours**.
SMARD's MAE over the full record, over the trailing year, over one weekend, and over the hours in
the top 1 % of residual load are four different numbers for the same forecast. This spec therefore
computes the hourly error once and treats every reported metric as an aggregate over a stated
window, always shown with its `hour_count`. The headline numbers are provisional: once the modelling spec
fixes its test window, SMARD is re-scored on those hours.

## Behaviour

### Setup

1. Repeat `team-EDA.ipynb` §1's loading and preparation: the data-directory resolver,
   `time_series`, `SERIES`, `DERIVED`, `YEARS`, the aggregation and plotting helpers, `DAY_NAMES`,
   the season mapping. One markdown cell states they are inherited and points at the source; no
   re-derivation.
2. State the duration convention once: every rule about a length of time is written as a duration
   and converted to an observation count from the measured resolution (Behaviour 28).

### Errors and their decomposition

3. Build a separate `errors` DataFrame on `time_series.index` — **not** columns on `time_series`,
   which keeps `SERIES + DERIVED` intact. It holds, per pair, the actual, the forecast and
   `err_{actual} = forecast − actual` (`err_residual_load`, `err_grid_load`, `err_renewables`) —
   the same pair columns as the hourly export (Behaviour 25) — plus the installed wind + solar
   capacity `cap_wind_solar = cap_wind_off + cap_wind_on + cap_solar`, so `window_metrics`
   (Behaviour 23) can compute nMAE and the capacity-normalised error from this one frame. State
   the sign convention in the notebook: **positive error / positive bias = over-forecast**, negative = under-forecast.
4. Verify, and print the maximum absolute deviation, that
   `fc_residual_load == fc_grid_load − fc_gen_wind_solar` holds in this record (it does, to SMARD's
   rounding, in the current snapshot). Together with the inherited actual-side identity this gives
   the exact decomposition `err_residual_load = err_grid_load − err_renewables`. State its
   consequence: a residual-load error is a load error minus a generation error, and an
   under-forecast of wind + solar shows up as an *over*-forecast of residual load.
5. Each metric uses **pairwise-complete hours** only: an hour enters a pair's metric only if both
   forecast and actual exist. `hour_count` is always the number of hours actually compared, per pair, per
   window.

### Metrics

6. For any set of hours, compute per pair: **MAE**, **RMSE**, **bias** (mean signed error), and
   **`hour_count`**. Every metric table in the notebook carries `hour_count` next to the values.
7. **Normalised MAE** `nMAE = MAE / mean(actual)` over the same window, in `%`, so the three pairs
   are comparable with each other. Report it at the full-record, trailing-365-day (including the rolling line in Behaviour 10),
   year, season and month levels. Do **not** report it for residual load at day level or in level bins: residual
   load's mean over short windows can be close to zero (the daily mean
   gets down to roughly 680 MWh in the current snapshot) and the ratio explodes there. State this
   rule in the notebook.
8. **Capacity-normalised generation error**: `err_renewables / cap_wind_solar` (Behaviour 3) per
   hour, aggregated to MAE and bias, in `% of installed capacity`. This is the
   measure that answers "did the wind + solar forecast get better?" across years, because absolute
   generation error grows with the fleet. Report it at year level and as the rolling line in Behaviour 10, never per month. Apply it to the
   generation pair only.
9. Report the **headline table**: pair × {full record, trailing 365 days} × {MAE, RMSE, bias,
   nMAE, `hour_count`}. The trailing 365 days end at the last hour where all three
   pairs are observed, derived from the data.

### Time slices

10. **Per month over the record**: MAE and bias per pair as monthly time series, using
    `_complete_periods` so the incomplete trailing month is dropped rather than shown as a fake dip or
    spike. One figure, one panel per pair, `style_timeseries`. Add a trailing-365-day rolling MAE
    line to separate trend from seasonality, plus two normalised rolling lines on the same rule: a
    rolling nMAE per pair, and a rolling capacity-normalised MAE for wind + solar (Behaviour 8).
    Every rolling line is evaluated at each month end over the preceding 365 days, and only once
    the record spans a full 365 days before that month end; earlier month ends stay empty rather
    than using a shorter window. These rolling lines are also the basis for every year-on-year
    statement: each point covers a full seasonal cycle, so partial years need no separate
    matched-window comparison.
11. **By hour of day** (local time): MAE and bias per pair, 0–23. Name the weakest hours per pair
    explicitly. Expect generation error to peak around solar midday and state whether it does.
12. **By season** (meteorological, inherited mapping): MAE, bias and nMAE per pair.
13. **By year**: MAE, bias, nMAE per pair, and capacity-normalised error for generation. Mark partial
    years (first or last) as partial; they are not compared against full years directly — the
    rolling MAE in Behaviour 10 covers that.
14. **State whether the forecast is getting better or worse**, per pair, from the rolling
    normalised lines in Behaviour 10: rolling nMAE for grid load, rolling capacity-normalised MAE
    for wind + solar, and for residual load both the rolling MAE and the rolling nMAE, read together
    with the decomposition (Behaviour 17). The year table (Behaviour 13) is context, not the basis
    of the verdict. A rise in absolute
    residual-load MAE is not by itself evidence of a worse forecast — it can come entirely from a
    larger generation fleet. Report the direction whichever way it comes out; the few years in the
    record do not support a precise trend, and the notebook must not claim one.

### Error by residual-load level

15. **Bins by actual residual-load level.** Edges are the quantiles
    `{1, 5, 10, 25, 50, 75, 90, 95, 99} %` of `residual_load` over the loaded record, plus `0`,
    sorted and de-duplicated. Print the edges in `MWh` with each bin's `hour_count`. The bins are a
    descriptive device, computed inside their cell — no bin column is written to `time_series` or
    `errors`. Per bin: MAE, RMSE, bias for residual load. Plot MAE and bias per bin.
16. **Regression-to-the-mean check.** Repeat Behaviour 15 with the **same MWh edges** applied to
    `fc_residual_load` instead of the actual. Show both views side by side and explain the
    difference in the notebook:
    - *Binned by actual* answers "when an extreme hour happened, how wrong was the forecast?" — the
      view that matters for **missed** risk. Even an unbiased forecast shows under-forecasting in the
      top bin and over-forecasting in the bottom bin here, purely because the bins select on the
      actual.
    - *Binned by forecast* answers "when the forecast predicted an extreme, how far off was it?" —
      the view that matters for **false alarms**.
    The gap between the two is the regression-to-the-mean effect, not a separate forecast defect.
    Only a tail degradation that survives in **both** views counts as a real weakness of the
    forecast.
17. **Decomposition per bin.** For each actual-level bin, report the bias of `err_grid_load` and
    `err_renewables` alongside `err_residual_load`. Bias decomposes exactly
    (`bias_res = bias_load − bias_gen`); MAE does not, so for the absolute size also report RMSE of
    each component and the correlation between the two component errors. State which component
    drives the tail error in each direction.
18. **State the finding plainly**, whichever way it comes out: is SMARD's forecast worse in
    the tails than on ordinary hours, in which direction, by how much, and does it survive the
    regression-to-the-mean check?

### Day extremes

19. Aggregate per calendar day (local `Europe/Berlin` date, the `DERIVED["date"]` boundary): the
    actual and forecast **day maximum** and **day minimum** of residual load, and the timestamp of
    each. A day enters only if both series meet the inherited day-completeness rule
    (`DAY_COMPLETENESS = 23 / 24` of the day's expected observations, see Inherited); otherwise its
    extremes are `NaN`.
20. Per day and direction: the **value error** (`fc_max − actual_max`, `fc_min − actual_min`, in
    `MWh`) and the **timing offset** (elapsed hours from the actual extreme's timestamp to the
    forecast extreme's timestamp, positive = forecast extreme later, in `h`). On ties, take the
    first occurrence and state it.
21. Report MAE, bias and `day_count` (the number of complete days compared) of the day-max and
    day-min value errors overall and per year. Plot the distribution of value errors and of
    timing offsets per direction.
22. Include one worked example in the notebook contrasting hourly MAE with day-extreme error on a
    single day, to show why the two are different questions: hourly MAE measures the shape of the
    day, day-extreme error measures what the risk label uses. The day is chosen from the data, not
    hardcoded: the complete day with the largest ratio of hourly MAE to `|day-max value error|` —
    the peak is nearly right while the hours around it are off. A zero day-max error counts as the
    largest ratio; on ties take the earliest day. Print the rule and the chosen date.

### Cascade

23. Define `window_metrics(errors, start=None, end=None, mask=None)` returning MAE, RMSE, bias, `hour_count`
    (and nMAE where Behaviour 7 allows it) per pair for any window or boolean hour mask. Every
    cascade table and slice in the notebook is built from this one function, so all metrics share one
    definition. RMSE is always recomputed from squared hourly errors — never averaged across
    sub-windows — and the notebook says so.
24. Build the cascade at fixed levels: full record, trailing 365 days, year, month, day. The day
    level is one row per forecast day (local calendar day) and also carries the day-extreme errors from
    Behaviour 20.

### Export

25. `data/metrics/smard_forecast_errors_hourly.csv`: one row per hour of `time_series`, `timestamp`, the actual
    and forecast value for each pair, and `err_residual_load`, `err_grid_load`, `err_renewables`.
    Missing forecasts stay empty. This file is what lets the modelling spec re-score SMARD on its own
    test hours.
26. `data/metrics/smard_forecast_errors_daily.csv`: one row per calendar day, per-pair MAE / RMSE / bias / `hour_count` over
    that day, and residual load's actual and forecast day max/min with their timestamps, value errors
    and timing offsets.
27. `data/metrics/smard_benchmark_metrics.csv`: the cascade above day level (full, trailing 365, year, month)
    plus the season slice (Behaviour 12), in long format — `level`, `period`, `pair`, `metric`, `value`, `hour_count`. All three
    files are plain CSV (`sep=","`, `decimal="."`, UTF-8), the same deliberate departure from the
    SMARD format that the risk-label exports use. All three go to `data/metrics/`, resolved from
    the same data directory as `data/smard.csv`; the notebook creates the folder if it is missing
    (`mkdir(exist_ok=True)`) rather than relying on the `.gitkeep`.

### Resolution independence

28. Every duration-based rule is a duration: day completeness is "23 of 24 hours" expressed as a

### Presentation and benchmark

29. Matplotlib for the time-series plots (with `style_timeseries`), seaborn where a hue plot is
    clearer. Every plot has a title, axis labels, explicit units, and one to three sentences of
    interpretation.
30. Close with a **"Findings"** section, then a separate **"Benchmark to beat"** section stating
    plainly:
    - the headline table (Behaviour 9) for residual load first, then grid load and wind + solar;
    - residual load's day-max and day-min MAE and bias;
    - the tail numbers: residual-load MAE and bias in the top and bottom bins by **actual** level,
      plus one sentence on whether the weakness also shows when binned by forecast level
      (Behaviour 16) — i.e. whether it is a real weakness or a selection effect;
    - that these numbers are **provisional**: the modelling spec re-scores SMARD on its own test
      window from `data/metrics/smard_forecast_errors_hourly.csv`, over exactly the same hours as its own model;
    - the **information-set caveat**, using SMARD's own publication rules (table in Data):
      SMARD's forecast covers **delivery day `D`, 00:00–23:00 local**, and is made on `D−1`. The
      grid-load forecast is published by **10:00** on `D−1`, the wind + solar forecast by **18:00** on
      `D−1` (Brussels time = `Europe/Berlin`), so `fc_residual_load` is complete only at 18:00 on

## Edge cases

- **Missing forecast hours.** In the current snapshot `fc_grid_load` and `fc_residual_load` miss one
  full day (2020-01-31, 24 h); `fc_gen_wind_solar` is complete. Handle this with the pairwise-complete
  rule (Behaviour 5), never by interpolation. The count comes from the data and must not be
  hardcoded: a re-fetch may add or remove gaps. That day's extremes are `NaN` under the completeness
  rule.
- **Forecasts ahead of actuals.** After a re-fetch the last rows may carry a forecast whose actual
  is not yet published. They are excluded by the pairwise rule, and the trailing-365-day window
  anchors on the last jointly observed hour, not on the last row.
- **nMAE near zero.** Residual load's mean over a short window can approach zero, and nMAE explodes
  there. Behaviour 7 restricts where it is reported; level bins use absolute `MWh` only.
- **Regression to the mean.** Binning by the actual makes any imperfect forecast look biased in the
  tails. Behaviour 16 exists so this is not reported as a forecast defect.
- **RMSE does not aggregate.** Averaging monthly RMSEs does not give the yearly RMSE. Every level is
  recomputed from hourly errors via `window_metrics`.
- **Small windows are noisy.** A single day is 24 hours, a tail level bin a few hundred. `hour_count` is shown
  with every metric; interpretation of cells with a small `hour_count` stays qualitative.
- **Capacity is a yearly step.** The `cap_*` columns carry one value per year, so fleet growth within
  a year is not reflected. This is why the capacity-normalised error is only reported over
  full-year windows — the year table and the trailing-365-day rolling line (Behaviour 8) — never
  per month.
- **Partial years.** A partial first or last year is marked as partial in the year table and never
  compared directly against full years; year-on-year statements come from the trailing-365-day
  rolling MAE (Behaviour 10).
- **Rolling MAE in the first year.** The trailing-365-day rolling MAE has no value until the record
  spans a full 365 days. Those month ends stay empty instead of being computed over a shorter
  window, which would cover only part of the seasonal cycle and bias the line — the same reasoning
  `risk-definition.ipynb` applies to its rolling threshold.
- **DST.** Spring-switch days have 23 hours and still count as complete; the hour-of-day slice has
  one fewer observation at local 02:00 per year, visible in `hour_count`. Timing offsets are elapsed hours
  between timezone-aware timestamps, not differences of hour-of-day numbers. The autumn fold is
  collapsed by SMARD and needs no handling.
- **Quantile edges move on re-fetch.** The level-bin edges are whole-record quantiles and shift when
  the record changes, like `risk-definition.ipynb`'s demoted `static` basis. This is acceptable because the bins are
  descriptive; they must never be reused as a label.
- **Information set.** SMARD's forecast and our model's forecast are only comparable at equal
  information cutoff and the same target day (Behaviour 30). The two components have different
  publication times (10:00 vs. 18:00 on `D−1`), so the residual-load forecast is effectively an
  18:00 forecast whose load part was fixed earlier. This spec states the caveat; it does not
  resolve it.
- **Revised load forecasts.** SMARD states that the grid-load forecast is updated whenever it
  changes by at least 10 %. The data does not show whether an archived `fc_grid_load` value is the
  original 10:00 value or a later revision, so the benchmark may carry slightly more information
  than a strict 10:00 snapshot. State this once in the benchmark section; it cannot be corrected
  from `data/smard.csv`.
- **Native resolution is quarter-hourly.** SMARD publishes both forecasts per 15 minutes; this
  record uses the hourly series. The metrics here are hourly metrics; quarter-hour errors would
  differ and are not comparable with these numbers (see Behaviour 28).
- **Missing data file.** A fresh clone has no `data/smard.csv`; the setup fails with a clear message
  naming `notebooks/API-connection.ipynb`.

## Acceptance criteria

### Setup and errors

- [ ] The notebook is `notebooks/02_forecast_metrics/forecast-metrics-claude.ipynb` and runs top to
      bottom from a fresh kernel against `data/smard.csv` alone.
- [ ] The shared setup is repeated from `team-EDA.ipynb` §1 and pointed at in one markdown cell.
- [ ] Errors live in a separate `errors` frame with the `forecast − actual` sign convention stated;
      `time_series` still holds exactly `SERIES + DERIVED`.
- [ ] The forecast-side identity is verified with its maximum deviation printed, and the error
      decomposition `err_res = err_load − err_gen` is stated.

### Metric reporting

- [ ] MAE, RMSE, bias and `hour_count` are reported for all three pairs, with `hour_count` next to every metric table.
- [ ] nMAE is reported only at the levels Behaviour 7 allows, and the reason is stated.
- [ ] Capacity-normalised generation error is reported at year level and as the trailing-365-day
      rolling line, never per month.
- [ ] The headline table covers full record and trailing 365 days, with the window end derived from
      the data.

### Slices

- [ ] Month-over-record, hour-of-day, season and year slices exist per pair, each with a written
      interpretation.
- [ ] The trailing-365-day rolling MAE, rolling nMAE and rolling capacity-normalised MAE are
      shown, partial years are marked, and no
      year-on-year statement compares a partial year directly against a full one.
- [ ] The notebook states per pair whether the forecast is improving or degrading, from the rolling
      normalised lines, without claiming a precise trend.
- [ ] Level bins by actual and by forecast level use the same printed MWh edges, and no bin column
      is persisted.
- [ ] The regression-to-the-mean difference between the two views is explained, and a tail weakness
      is only claimed if it shows in both.
- [ ] The component bias decomposition per bin is reported, and the driving component is named per
      direction.

### Day extremes and cascade

- [ ] Day max/min value errors and timing offsets are computed for every complete day, and reported
      overall and per year.
- [ ] One worked example contrasts hourly MAE with day-extreme error, on the day chosen by
      Behaviour 22's rule, with the rule and date printed.
- [ ] `window_metrics` is the single source of every metric; RMSE is never averaged across windows.
- [ ] The cascade exists at full, trailing 365, year, month and day level.

### Export and benchmark

- [ ] `data/metrics/smard_forecast_errors_hourly.csv`, `data/metrics/smard_forecast_errors_daily.csv` and
      `data/metrics/smard_benchmark_metrics.csv` are written as plain comma/period CSV with the columns in
      Behaviours 25–27.
- [ ] The self-check in Behaviour 31 passes.
- [ ] Every plot has a title, axis labels, explicit units and a written interpretation.
- [ ] The "Benchmark to beat" section states the headline, day-extreme and tail numbers, that they
      are provisional, how to re-score on another window, the information-set caveat and the
      revised-load caveat, and whether the tail weakness survives the binned-by-forecast view.

### Discipline

- [ ] No literal calendar year or date appears in code; examples and windows are derived from the
      data.
- [ ] Every duration rule is a duration, not a row count.
- [ ] No risk-label file is read; no risk flag is computed on `fc_residual_load`; no hit/miss,
      precision or recall appears. 04.3 is referenced, not run.
- [ ] No MAPE appears for any pair.
- [ ] No naive baseline is computed; 04.1 is referenced, not run.
- [ ] No ISO-week level, zoom demo or tolerance share appears anywhere, including the benchmark;
      04.2 is referenced, not run.
- [ ] No model is fitted, no split is chosen, no MLflow run is logged.
- [ ] `team-EDA.ipynb`, `risk-definition.ipynb` and all `01_eda/` notebooks are unchanged.
- [ ] No new dependency is added; if one appears necessary, it is raised rather than `uv add`-ed.
