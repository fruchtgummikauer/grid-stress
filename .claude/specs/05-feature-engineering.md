## Goal

The project needs a lean, leakage-safe feature set to forecast `residual_load` one day ahead. Per
[CLAUDE.md](../../CLAUDE.md), generation features are limited to wind + solar, and SMARD's own
`fc_residual_load` is the benchmark our model has to beat — so it must never be used as a model
input, only as the comparison target scored separately (per
[04-forecast-metrics.md](04-forecast-metrics.md)).

Concretely, this spec:

1. States the **forecast-origin contract**: for a target day `D`, a feature may only use
   `Forecast Wind + Solar` for `D` itself (the one genuine day-ahead forecast in scope) plus actual
   history strictly before `D`'s first hour, and calendar facts about `D`. Nothing from `D`'s
   actual `grid_load`, `renewables` or `residual_load` may appear as an input.
2. Builds a fixed set of **12 features**, grouped by daily / weekly / seasonal pattern and by type
   (calendar, cyclical encoding, lag, rolling statistic, capacity-normalised ratio,
   forecast-derived) — see the Data section for the full table.
3. Documents the **2 features considered and dropped**, and why, so the decision is not silently
   lost.
4. Verifies the origin-safety of every engineered column with an explicit self-check (no feature's
   underlying timestamp is on or after its target hour).
5. Exports the feature matrix as one CSV the modelling spec can load directly.

Success means the modelling spec can load `data/features/residual_load_features.csv`, join it to
`residual_load` (the target) and to the risk labels, and start fitting a model without re-deriving
any feature or re-litigating the leakage rules.

## Behaviour

### Setup

1. Repeat `team-EDA.ipynb` §1's loading and preparation in one markdown cell pointing at the
   source; no re-derivation.

### Feature construction

2. Build a separate `features` DataFrame on `time_series.index`, one column per feature in the
   Data table below.
3. **Calendar / cyclical features** (`hour_sin/cos`, `dow_sin/cos`, `doy_sin/cos`, `is_weekend`,
   `is_holiday`, `season`) are computed directly from `DERIVED` columns and the target day's own
   calendar — always safe, since they describe `D` itself, not any measurement of it.
4. **Lag and rolling features** (`residual_load_lag_24h`, `residual_load_lag_168h`,
   `residual_load_roll_mean_72h`, `residual_load_roll_std_168h`, `vre_capacity_factor_lag_24h`) are
   computed with `.shift()` / trailing `.rolling()` windows whose **last included hour is strictly
   before `D`'s first hour** — never a window that reaches into the target day.
5. **Forecast-derived features** (`forecast_wind_solar`, `forecast_wind_solar_error_lag_24h`) use
   `Forecast Wind + Solar` for `D` itself (genuinely published ahead) and the lagged forecast error
   from `04-forecast-metrics.md`'s `err_renewables` column, shifted 24h back.
6. State the **origin-safety rule** once in a markdown cell: a feature for target hour `t` may only
   read source data with a timestamp `< t`'s calendar day start, except the two forecast-derived
   features, which may read `Forecast Wind + Solar` at exactly `t`.

### Self-check

7. A self-check cell asserts, per feature column: the maximum source timestamp used to compute any
   row's value is strictly before that row's own timestamp — except the two forecast-derived
   columns, which are allowed to equal it. Also assert `features` has exactly `len(time_series)`
   rows on the same index, and that `time_series` itself is unchanged (`SERIES + DERIVED` only).

### Export

8. `data/features/residual_load_features.csv`: one row per hour of `time_series`, `timestamp` plus
   the 12 feature columns. Plain CSV (`sep=","`, `decimal="."`, UTF-8), the project's derived-file
   convention. The notebook creates `data/features/` if missing.

## Data

### Features (12)

| Pattern | Feature | Definition | Available at origin? | Rationale |
|---|---|---|---|---|
| Daily | `hour_sin`, `hour_cos` | `sin/cos(2π·hour/24)` for target hour | calendar fact | smooth daily cycle, no midnight discontinuity |
| Daily | `is_weekend` | 1 if target day is Sat/Sun | calendar fact | weekday/weekend load shape differs |
| Daily | `is_holiday` | `holidays.country_holidays("DE")` flag for target day | calendar fact | holidays behave like weekends |
| Weekly | `dow_sin`, `dow_cos` | `sin/cos(2π·dow/7)` for target day | calendar fact | weekly rhythm without 7 dummies |
| Weekly | `residual_load_lag_168h` | actual `residual_load` 168h (7 days) before target hour | strictly past | same weekday/hour last week, strong persistence signal |
| Seasonal | `doy_sin`, `doy_cos` | `sin/cos(2π·day_of_year/365.25)` for target day | calendar fact | smooth annual cycle |
| Seasonal | `season` | meteorological season of target day (inherited mapping) | calendar fact | coarse seasonal bucket for tree models |
| Lag | `residual_load_lag_24h` | actual `residual_load` 24h before target hour | strictly past | short-term persistence/regime continuation |
| Rolling | `residual_load_roll_mean_72h` | trailing 72h mean, window ending before target day | strictly past | smoothed recent level |
| Rolling | `residual_load_roll_std_168h` | trailing 7-day std dev, window ending before target day | strictly past | recent volatility, candidate stress signal |
| Capacity-normalised | `vre_capacity_factor_lag_24h` | `(wind_off + wind_on + solar) / (cap_wind_off + cap_wind_on + cap_solar)`, 24h before target hour | strictly past | recent renewable-penetration regime |
| Forecast-derived | `forecast_wind_solar` | `Forecast Wind + Solar` (`fc_gen_wind_solar`) for the target day itself | published ahead (by 18:00 on `D−1`) | direct driver of tomorrow's residual load; the one genuine look-ahead input |
| Forecast-derived | `forecast_wind_solar_error_lag_24h` | `err_renewables` (from `04-forecast-metrics.md`), 24h before target hour | strictly past | recent forecast-reliability signal |

### Dropped candidates (2)

| Feature | Definition | Reason dropped |
|---|---|---|
| `wind_solar_lag_24h` | `(wind_off + wind_on + solar)` 24h before target hour | Redundant with `vre_capacity_factor_lag_24h`, which carries the same recent-generation information already normalised by installed capacity — keeping both adds correlated features without new signal. |
| `wind_solar_share` | `(wind_off + wind_on + solar) / grid_load` at the same hour | Requires `grid_load` for the target hour itself, which is not known at origin (no grid-load forecast is in scope) — would be a leakage risk if computed for `D` and provides no safe substitute, so it is dropped rather than reworked into a lagged form that would duplicate `vre_capacity_factor_lag_24h`. |

### Explicitly excluded (not candidates, not dropped)

| Column | Reason |
|---|---|
| `Forecast Grid Load` (`fc_grid_load`) | Out of scope for this dataset selection; no grid-load forecast is used as a feature. |
| `Forecast Residual Load` (`fc_residual_load`) | The benchmark to beat (per CLAUDE.md and `04-forecast-metrics.md`); using it as a feature would make the model dependent on SMARD's own forecast and defeat the comparison. Retained in the pipeline only for evaluation. |
| `Residual Load`, `Grid Load`, `Wind`, `Solar` for the target day itself | These are the outcome (or its components) for `D` — never available at origin, never inputs. |

## Edge cases

- **Missing forecast hours.** `fc_gen_wind_solar` has no known gaps in the current snapshot
  (per `04-forecast-metrics.md`); `forecast_wind_solar` stays empty for any hour where it is
  missing, never interpolated.
- **Lag/rolling warm-up.** The first 168 hours (and the first 72h/24h for shorter windows) of the
  record cannot have a lag or rolling feature computed; those rows stay `NaN`, not zero-filled.
- **DST.** `time_series`'s index is Berlin-local wall-clock time with the spring-DST hour genuinely
  missing (not a UTC-backed continuous index — CLAUDE.md's `spans_gap`), so lags are implemented as
  a **wall-clock shift** ("same local hour, N hours/days earlier"), matching the project's
  `D−7`-persistence convention (`04.1-naive-baseline.md`), not a row-count shift. A consequence
  discovered while running this spec: the two rolling features (`roll_mean_72h`, `roll_std_168h`)
  additionally reject every day whose trailing window spans a spring-DST transition — that window
  is one hour short of `min_periods`, so it is correctly left `NaN` rather than silently computed
  from 71/167 hours. This adds 3 extra `NaN` days per year for the 72h window and 7 for the 168h
  window, on top of the initial warm-up (verified in the notebook: 27 and 63 `NaN` days
  respectively across the current 8-DST-transition record — 3+8×3 and 7+8×7).
- **`vre_capacity_factor_lag_24h` and yearly capacity steps.** `cap_*` columns are a yearly step
  value (per CLAUDE.md); the ratio still uses the correct year's capacity because it is looked up
  at the same historical hour as the generation values, not at the target hour.
